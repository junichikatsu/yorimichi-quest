# 第1部 概要編

## 1. 背景と目的

### 1.1 解決したい課題

ピッチ資料「解決すべき3つの社会的課題（Problem Space）」に対応する。

1. **ミクロデータの圧倒的不足**：行政オープンデータは避難所の位置等の基本情報に留まり、「トイレの段差・レバー形状」「車いす対応」「オストメイト設備」など、要配慮者の命綱となる詳細データが存在しない。行政側は悉皆調査のコストをかけられず、街の動的な変化（設備の故障・撤去等）に追随できないため、情報が陳腐化し続ける。
2. **防災アプリの形骸化**：既存の防災アプリは有事にしか開かれず、平時の認知・使い方学習が進まないため、いざという時にスムーズに活用されない。
3. **有事の避難リスク**：1と2が重なり、大災害時に「自分や家族にとって本当に安全な避難先・ルート」が分からない。特に要配慮者を抱える世帯で致命的なリスクとなる。

> 課題1〜3は独立ではなく、「データ不足（1）× 平時の訓練不足（2）→ 有事のリスク（3）」という因果構造を持つ。本サービスは1と2を同時に解くことで3を解消する。

### 1.2 目的

日常の「寄り道」「散歩」で楽しめる位置情報ゲームを通じて、

- 市民が**無意識のうちに避難ルート・防災知識を習得**し、
- 市民自身の投稿によって**防災・バリアフリーのミクロデータを収集・検証**し、
- その成果を**行政へ「プレゼント」として還元**する

「平時・有事デュアルモード型」シビックテック・プラットフォームを実現する。

## 2. サービス概要

| モード | 概要 |
| :--- | :--- |
| 平時モード（ゲーム） | LINEミニアプリ上の位置情報ゲーム。避難所チェックイン、現地クイズ、写真投稿ミッションでポイント・称号を獲得。投稿写真はVision AIが自動解析し、バリアフリー属性を構造化データとして蓄積。 |
| 有事モード（ライフライン案内） | 災害時に「災害ライフラインモード」へ切替。平時に蓄積したデータをもとに、避難所・水・電源・バリアフリー情報をマップで案内。 |
| 行政還元ダッシュボード | 収集データをヒートマップ・スコアリングで可視化し、データ空白地帯や優先整備箇所を行政へ提示。 |

### 2.1 独自の価値提案（UVP）と競争優位

> **「日常の『寄り道』を、都市を救う防災データに変える」**
> 平時は遊びながら無意識に防災訓練・データ収集を行い、有事は最強のライフライン案内に切り替わる「デュアルモード体験」。

競争優位（Unfair Advantage）は次の2点であり、要件上も中核として扱う。

| # | 優位性 | 対応する要件 |
| :--- | :--- | :--- |
| UA-1 | **超低コストのデータ収集**：市民の「遊び」が原動力となり、行政の調査予算に依存せずミクロデータが集まる | FR-02〜FR-05、FR-07（ゲーミフィケーション／インセンティブ） |
| UA-2 | **高精度検証：AI×群集心理の相互クイズ**：AI一次判定と、他ユーザーによる現地確認クイズの二段構えで精度を担保 | FR-05-2〜FR-05-5、**FR-06（相互検証）** |

> UA-2 を支える FR-06 は、単なる付加機能ではなく「収集データが行政に使える品質である」ことの根拠である。MVPでは実装規模の都合で優先度 Should とするが、**デモシナリオには必ず1件の検証済みデータを含める**こと（5章 成功基準）。

## 3. スコープ定義

### 3.1 MVP（本書の要件定義対象：8/22-23 集中開発〜First Stage）

| # | 領域 | MVPでの実現レベル |
| :--- | :--- | :--- |
| 1 | 平時モード | コア体験（マップ→チェックイン→クイズ／写真投稿→AI解析→ポイント獲得）をフル実装 |
| 2 | 有事モード | **手動切替によるデモ画面**。蓄積データを使ったライフラインマップ表示までを実装（災害検知による自動切替は対象外） |
| 3 | 行政ダッシュボード | **静的な可視化デモ**（収集データのヒートマップ・一覧表示）。行政側の操作機能・SaaS機能は対象外 |
| 4 | AI画像解析 | 投稿写真からのバリアフリー属性抽出・タグ付け、不適切画像の一次フィルタリング |
| 5 | AIクイズ生成 | 現在地・周辺スポット情報に基づくクイズの自動生成（簡易版。過去行動ログによる高度なパーソナライズは対象外） |
| 6 | 相互検証 | 他ユーザー投稿への「現地確認クイズ」による二次検証（コンセンサスは単純な賛成数閾値方式）。競争優位UA-2の実体のため、最小成立ラインは必須実装 |
| 7 | 計測（KPI） | DAU/MAU・新規／更新スポット数・検証済み率を集計できる状態を作る（専用分析基盤は導入しない） |

### 3.2 MVPスコープ外（将来拡張要件）

以下は企画書に記載のある構想だが、MVPでは**実装しない**。要件は「12. 将来拡張要件」に整理する。

- 東京ポイント（東京都公式）との実連携 → **アプリ内独自ポイントで代替**
- LINEミニアプリの正式審査・公開 → **未認証（開発版）ミニアプリで動作**
- 災害情報API連動による有事モード自動切替
- オープンバッジ（外部規格）発行、地域加盟店クーポン交換
- マネタイズ機能（公式アピール枠・B2Bデータライセンス・行政向けSaaS）
- 縄張り争いのシーズン制、避難所混雑度等のリアルタイム有事運用

### 3.3 外部連携の代替方針

| 企画書上の構想 | MVPでの代替 |
| :--- | :--- |
| 東京ポイント連動 | アプリ内独自ポイント「YORIポイント」。将来の東京ポイント連携を見据え、付与ロジックはポイント種別を抽象化して実装 |
| LINEミニアプリ正式公開 | LINE Developersの未認証ミニアプリ（開発版）＋LIFFで動作。デモはチームのLINEアカウントで実施 |
| オープンデータAPIリアルタイム連携 | 公開CSV/GeoJSONを事前に取込・正規化したデータベース（D1）から配信 |

## 4. ターゲットユーザー（顧客セグメント）

本サービスは「データを集める側」と「データを使う側」からなる**二面市場**として設計する。片側だけでは成立しないため、MVPでも両者の体験を最低限成立させる（データ活用者側は閲覧デモの範囲）。

### 4.1 データ収集者（市民プレイヤー）

| ペルソナ | 概要 | MVPでの主要ユースケース |
| :--- | :--- | :--- |
| ① アクティブな寄り道プレイヤー（20-30代・位置ゲー好き）※アーリーアダプター | 防災意識は高くないがゲームとして遊ぶ | 散歩中に未調査スポットへ寄り道し、チェックイン・クイズ・写真投稿でポイントと称号を獲得 |
| ② アクティブシニア＆地域見守り層（60-70代・毎日散歩）※アーリーアダプター | 地域貢献・健康維持が動機 | 散歩ルート上の設備を点検・チェックインし、貢献の「ありがとう」通知を受け取る |

### 4.2 データ活用者

| セグメント | 概要 | MVPでの主要ユースケース |
| :--- | :--- | :--- |
| ③ 要配慮者の家族（車いすユーザー家族・子育て世代）※アーリーアダプター | バリアフリー情報の**閲覧者**として利用。有事の命綱として活用 | マップで詳細なバリアフリー写真・属性を確認し、平時の外出・有事の避難計画に活用（FR-02、FR-08-4） |
| ④ 自治体（防災課・都市計画・福祉） | 調査予算・人手不足でデータが陳腐化。市民からの非難ではなく協力関係を求めている | 還元ダッシュボードでデータ空白地帯・優先整備箇所を確認、CSVでオープンデータとして再公開（FR-09） |
| ⑤ ナビ／物流企業・地域店舗 | 高解像度のバリア情報を必要とする／バリアフリー対応をPRしたい | **MVPスコープ外**。EX-07（B2Bデータライセンス・公式アピール枠）で対応 |

> セグメント④⑤への提供価値（高機能SaaS・B2BデータAPI・店舗公式アピール枠）は収益モデルに直結するが、MVPでは④の**閲覧デモのみ**を実装する（3.1 #3）。⑤は将来拡張（12章 EX-06/EX-07）。

## 5. 成功基準（MVP）

### 5.1 デモ・検証の成功基準

| 観点 | 基準 |
| :--- | :--- |
| デモ成立 | 「マップ表示→スポット到達→チェックイン→写真投稿→AI解析結果表示→ポイント獲得→ダッシュボード反映→有事モード切替」の一連フローが実機（LINEアプリ）で通しで動作する |
| AI解析 | 代表的な設備写真（バリアフリートイレ・AED・避難所入口）から主要属性が抽出・表示される |
| 相互検証（UA-2） | デモシナリオ内で、他ユーザーの確認クイズ回答により1件以上のデータが「検証済み」へ遷移し、ダッシュボード／CSV出力に反映される |
| PSF検証 | ヒアリング対象者（5名以上）がAlpha版を操作し、思考発話法で「日常的に使いたい」熱量の有無を確認できる |
| First Stage | 2分ピッチ動画内で実機デモ映像を使用できる |

### 5.2 重要指標（KPI）

ピッチ資料リーンキャンバスの「重要指標」に対応する。MVP期間中は実測値の獲得よりも**計測できる状態を作ること**（FR-11）を目標とする。

| # | 指標 | 定義 | MVPでの扱い |
| :--- | :--- | :--- | :--- |
| KPI-1 | DAU / MAU | 日次／月次のアクティブユーザー数（1回以上のAPIアクセス） | 計測基盤を実装し、デモ期間の実績値を取得 |
| KPI-2 | 新規スポット数 | 期間内に初めて投稿・属性付与されたスポット数 | 計測基盤を実装し、ダッシュボードに表示 |
| KPI-3 | 更新スポット数 | 期間内に新たな投稿・検証で情報が更新されたスポット数 | 同上 |
| KPI-4 | 検証済み率 | 公開投稿のうち検証済みに到達した割合（UA-2の実効性指標） | 計測基盤を実装 |
| KPI-5 | SaaS導入自治体・企業数 | 有償契約数 | **MVPでは計測対象外**（EX-07以降） |

# 第2部 詳細編

## 6. システム全体構成

```
[ユーザー] ─ LINEアプリ
     │
     ▼
┌──────────────────────────────────────┐
│ LINEミニアプリ / LIFF（フロントエンド）        │
│  - SPA（マップUI: Mapbox GL JS または Leaflet）│
│  - LIFF SDK（認証・プロフィール・位置情報）      │
└──────────────────────────────────────┘
     │ HTTPS / REST API (JSON)
     ▼
┌──────────────────────────────────────┐
│ Cloudflare Workers（バックエンドAPI）          │
│  - Hono 等の軽量フレームワーク                  │
│  - D1: リレーショナルDB（スポット・投稿・ユーザー）│
│  - R2: 投稿写真ストレージ                       │
│  - Workers AI / 外部Vision API: 画像解析         │
│  - LLM API: クイズ生成                          │
└──────────────────────────────────────┘
     │
     ▼
┌──────────────────────────────────────┐
│ 行政還元ダッシュボード（Web / 閲覧専用）        │
│  - 収集データのヒートマップ・一覧・スコア表示    │
└──────────────────────────────────────┘
```

### 6.1 技術スタック

| レイヤ | 技術 | 備考 |
| :--- | :--- | :--- |
| フロントエンド | LIFF (LINE Front-end Framework) + SPA（TypeScript） | フレームワークはチーム習熟度で選定（React/Vue等） |
| マップ | Mapbox GL JS または Leaflet + OSMタイル | 無償枠・ライセンスを確認して選定 |
| バックエンド | Cloudflare Workers（TypeScript） | REST API |
| DB | Cloudflare D1（SQLite互換） | 位置検索は緯度経度の矩形絞り込み＋距離計算で対応 |
| ストレージ | Cloudflare R2 | 投稿写真（リサイズ後） |
| 画像解析AI | マルチモーダルLLM API（例：Claude Vision）または Workers AI | 属性抽出＋不適切判定 |
| クイズ生成AI | LLM API | プロンプトテンプレート＋スポット属性を入力 |
| ダッシュボード | 静的Web（Cloudflare Pages）＋同一API参照 | 閲覧専用 |

## 7. 機能要件

優先度は MoSCoW（**M**ust / **S**hould / **C**ould）で表記。Must はハッカソン2日間で完成必須、Should はFirst Stage収録までに追加、Could は余力があれば。

### FR-01 認証・ユーザー管理

| ID | 要件 | 優先度 |
| :--- | :--- | :--- |
| FR-01-1 | LIFFによるLINEログインで認証する。初回ログイン時にユーザーを自動登録する | M |
| FR-01-2 | LINEプロフィール（表示名・アイコン）をアプリ内で利用する | M |
| FR-01-3 | ユーザーごとに累計ポイント・称号・投稿履歴を保持する | M |
| FR-01-4 | 位置情報の利用について初回に同意画面を表示する | M |

### FR-02 マップ・スポット表示（平時モード）

| ID | 要件 | 優先度 |
| :--- | :--- | :--- |
| FR-02-1 | 現在地を中心としたマップを表示し、周辺のスポット（避難所・AED・バリアフリートイレ・給水スポット等）をカテゴリ別アイコンでピン表示する | M |
| FR-02-2 | スポットをタップすると詳細（名称・カテゴリ・属性タグ・投稿写真・検証状況）を表示する | M |
| FR-02-3 | データ空白地帯（投稿・検証数が少ないスポット）を「未開拓ゾーン」として強調表示する | S |
| FR-02-4 | 未開拓ゾーンのスポットはポイント倍率（2〜3倍）を表示する | S |
| FR-02-5 | カテゴリでのフィルタ表示ができる | C |

### FR-03 チェックイン

| ID | 要件 | 優先度 |
| :--- | :--- | :--- |
| FR-03-1 | スポットから半径100m以内（閾値は設定可能）にいる場合のみチェックインできる | M |
| FR-03-2 | チェックイン成功時にポイントを付与し、演出（アニメーション等）を表示する | M |
| FR-03-3 | 同一スポットへの再チェックインは一定時間（例：24時間）制限する | M |
| FR-03-4 | スポットごとのチェックイン回数・貢献度を記録し、最多貢献者に「防災マスター」称号を付与する | S |

### FR-04 クエスト・クイズ

| ID | 要件 | 優先度 |
| :--- | :--- | :--- |
| FR-04-1 | チェックイン時に、そのスポットに関するクイズ（例：AEDの設置場所、水害時の適否）を出題する | M |
| FR-04-2 | クイズはスポット属性・周辺情報をもとにLLMが自動生成する（生成結果はキャッシュし、同一スポットで再利用可） | M |
| FR-04-3 | 正解時にボーナスポイントを付与する | M |
| FR-04-4 | 現在地周辺のハザード文脈を踏まえた避難シミュレーションクイズを生成する（例：「大雨時に向かうべき最寄り避難所は？」） | S |
| FR-04-5 | 行政課題と連動したミッション・イベント（例：「AEDを3つ発見せよ」）を運営が登録・配信できる | C |

### FR-05 写真投稿・AI解析

| ID | 要件 | 優先度 |
| :--- | :--- | :--- |
| FR-05-1 | チェックイン中のスポットに対して設備写真（トイレ内部・入口・AED等）を投稿できる | M |
| FR-05-2 | 投稿写真をVision AIで解析し、バリアフリー属性（車いす対応／オストメイト／点字ブロック／段差の有無・目安高さ／手すり等）を自動抽出してタグ候補として提示する | M |
| FR-05-3 | ユーザーはAI抽出タグを確認・修正して確定できる（AI出力を無検証で確定させない） | M |
| FR-05-4 | AIが不適切画像（設備と無関係・人物中心・不快コンテンツ）と判定した投稿は保留とし、公開しない | M |
| FR-05-5 | 投稿時のGPS位置とスポット位置の整合性を検証する（乖離が大きい場合は受け付けない） | M |
| FR-05-6 | 写真は個人情報保護のためサーバー側で顔・ナンバープレートを含む場合に保留扱いとする（AI判定） | S |
| FR-05-7 | 画像はアップロード時にリサイズ・EXIF位置情報除去を行って保存する | M |

### FR-06 相互検証（コンセンサス）

本機能は競争優位 UA-2（AI×群集心理の相互クイズ）の実体であり、収集データの品質を担保する根拠となる。最小成立ライン（FR-06-1・FR-06-2）はMustに引き上げる。

| ID | 要件 | 優先度 |
| :--- | :--- | :--- |
| FR-06-1 | 他ユーザーの投稿に対し、現地で「この設備は実在し、情報は正しいか？」の確認クイズ（はい／いいえ＋コメント）に回答できる | M |

## 9. データモデル（論理）

主要エンティティのみ。詳細な物理設計は設計工程で確定する。

```
users              ユーザー（LINE userId、表示名、累計ポイント、属性設定、最終アクティブ日時）
spots              スポットマスタ（名称、カテゴリ、緯度経度、出典、出典取得日、初回データ付与日時、最終更新日時）
spot_attributes    スポット属性タグ（車いす対応等、値、ステータス: AI提案/ユーザー確定/検証済み、由来投稿ID）
checkins           チェックイン（ユーザー、スポット、日時、位置）
posts              写真投稿（ユーザー、スポット、R2キー、AI解析結果JSON、ステータス: 保留/公開/却下）
verifications      相互検証（投稿、ユーザー、賛否、コメント）
quizzes            クイズ（スポット、問題文、選択肢、正解、生成元、キャッシュ用）
quiz_answers       回答履歴（ユーザー、クイズ、正誤）
point_logs         ポイント履歴（ユーザー、種別、行動種別、増減、日時）
titles             称号（ユーザー、スポット、称号名、期間）
notifications      アプリ内通知（ありがとう通知等）
```

> KPI（5.2）は専用の分析テーブルを設けず、上記テーブルの日時列を一次ソースとして集計する（FR-11）。`spots.初回データ付与日時 / 最終更新日時` は新規・更新スポット数の算出に用いる。

### データステータス遷移（投稿・属性）

```
投稿 → AI一次判定 ─ NG → 保留/却下
              └ OK → 公開（属性は「AI提案→ユーザー確定」）
                        └ 相互検証 賛成が閾値到達 → 検証済み → ダッシュボード/CSV出力対象
```

## 13. 前提条件・制約

- LINE Developersアカウント・LIFFアプリ（開発版）をチームで用意できること。
- Vision/LLM APIの利用キーと予算（デモ規模の従量課金）を確保すること。
- オープンデータはデモ対象エリア分を8/22までに取込済みにすること（FR-10）。
- 実機デモはLINEアプリ上で行う。未認証ミニアプリのため、参加者以外への一般公開は行わない。
- 位置偽装（GPSスプーフィング）への完全な対策はMVPでは行わない（位置整合性チェックのみ）。

## 14. リスクと対応

| リスク | 影響 | 対応 |
| :--- | :--- | :--- |
| ハッカソン2日間でMust要件が完了しない | デモ不成立 | 事前準備（8/22以前）でオープンデータ取込・LIFF疎通・AI解析のPoCを済ませ、当日は結合とUIに集中する |
| Vision AIの属性抽出精度が不十分 | デモ品質低下 | デモ用写真セットで事前にプロンプトをチューニング。タグはユーザー修正可能な設計（FR-05-3）で精度不足を吸収 |
| D1の地理検索性能 | マップ表示遅延 | 矩形絞り込み＋インデックスで対応。デモエリア限定でデータ量を制御 |
| 不適切投稿がデモ中に発生 | 信頼性毀損 | AI一次フィルタ＋保留フロー（FR-05-4）。デモはクローズド環境で実施 |
| LIFFの位置情報取得の精度・拒否 | チェックイン不可 | 位置許可の導線を丁寧に設計。デモ用に閾値を緩和できる設定を持つ |
| 参加人数が少なく相互検証（UA-2）が閾値に達しない | 競争優位の実証ができず、検証済みデータが0件になる | デモでは検証閾値を賛成1〜2件に設定可能にする。チームメンバーによる検証回答をシナリオに組み込み、必ず1件は検証済みに到達させる（5.1） |
| データ活用者（ペルソナ③・自治体）側の価値がデモで伝わらない | 二面市場のうち片側のみの訴求となり、協創ストーリーが弱くなる | ピッチ・デモ構成に「収集→ダッシュボード反映→要配慮者が閲覧」の受け手側カットを必ず含める |

# 第1部 概要編

## 1. 背景と目的

### 1.1 解決したい課題

ピッチ資料「解決すべき3つの社会的課題（Problem Space）」に対応する。

1. **ミクロデータの圧倒的不足**：行政オープンデータは避難所の位置等の基本情報に留まり、「トイレの段差・レバー形状」「車いす対応」「オストメイト設備」など、要配慮者の命綱となる詳細データが存在しない。行政側は悉皆調査のコストをかけられず、街の動的な変化（設備の故障・撤去等）に追随できないため、情報が陳腐化し続ける。
2. **防災アプリの形骸化**：既存の防災アプリは有事にしか開かれず、平時の認知・使い方学習が進まないため、いざという時にスムーズに活用されない。
3. **有事の避難リスク**：1と2が重なり、大災害時に「自分や家族にとって本当に安全な避難先・ルート」が分からない。特に要配慮者を抱える世帯で致命的なリスクとなる。

> 課題1〜3は独立ではなく、「データ不足（1）× 平時の訓練不足（2）→ 有事のリスク（3）」という因果構造を持つ。本サービスは1と2を同時に解くことで3を解消する。

### 1.1.1 課題の実測値（ヒアリング n=37）

上記3課題は仮説ではなく実測値で裏付けられている。詳細は [都民ヒアリング集計](hearing-citizens.md)（一般都民37名・2026-08-07〜14）。

| 課題 | 実測値 |
| :--- | :--- |
| **課題1** ミクロデータの不足 | 最寄りの避難所の**場所**が浮かぶ人は **67.6%（25/37）**。一方で**場所以外の情報**（水害対応・混雑状況・トイレ設備など）を知る人は **16.2%（6/37）**。**場所が浮かぶ25人のうち76.0%が名前しか知らない** |
| **課題2** 防災アプリ・行政情報の形骸化 | 自治体ホームページを直近3ヶ月に閲覧した人は 32.4%、**うち防災目的は2人（全体の5.4%）**。行政が情報を公開しても防災目的で見に行く市民は20人に1人しかいない |
| **課題3** 有事の避難リスク | 通信障害でネットに繋がらない場合、避難所やルートが頭に浮かばない人は **40.5%（15/37）** |
| **要配慮者側の課題**（4.3 ペルソナ④） | ベビーカー・車椅子で「通れるか不安で遠回りした」経験は、**未就学児または要配慮者がいる10人中6人（60.0%）**。**いずれもいない27人では0件** |

> 最後の行は、困りごとが**当事者層に完全に閉じている**ことを示す。当事者以外に見えないため行政も把握しづらく、オープンデータにも現れない。これが課題1の構造的な原因である。
>
> なお **サービス前提の検証**も同調査で取れている。週2回以上街を歩く人は 91.9%、街で写真を撮ったことがある人は 75.7% であり、日常の移動に乗せる設計（P-2）と写真投稿（FR-05）の行動前提は成立する。一方で**直近1週間に寄り道した人は 24.3% にとどまる**が、その理由はいずれも「なんとなく別の道を通ってみた」「気分転換」など目的のない軽いものであり、「寄り道のきっかけが街に存在していない」と読むべきである（詳細は集計ファイル）。

### 1.2 目的

日常の「寄り道」「散歩」で楽しめる位置情報ゲームを通じて、

- 市民が**無意識のうちに避難ルート・防災知識を習得**し、
- 市民自身の投稿によって**防災・バリアフリーのミクロデータを収集・検証**し、
- その成果を**行政へ「プレゼント」として還元**する

「平時・有事デュアルモード型」シビックテック・プラットフォームを実現する。

本サービスの要点は次の2つに集約される。要件はこの2点に貢献するかで優先度を判断する。

| # | 要点 | 対応する要件 |
| :--- | :--- | :--- |
| P-1 | **行政データの不足を補う**：行政オープンデータに存在しない項目を特定し、市民の投稿で埋めて行政へ還元する | FR-05（写真投稿・AI解析）、FR-06（相互検証）、FR-09（還元ダッシュボード）、**FR-12（欠損抽出とクエスト化）** |
| P-2 | **防災意識の低い層に、ゲームとインセンティブで防災情報をインプットする** | FR-02〜FR-04（マップ・チェックイン・クイズ）、FR-07（ポイント・称号・シェア）、**FR-14（カードコレクション）**、**FR-13（イベント発生）**、FR-08-7（有事モードでの記憶の呼び起こし）。設計方針は 2.2 |

> P-1 の担い手は初期ターゲット（フェーズ1：防災コミット層）、P-2 の対象は拡大ターゲット（フェーズ2：一般層）である（4.1）。

**要点を2つに絞る理由**：構想を広げると、短い開発期間（8/22-23）で発散し、かつ First Stage の2分ピッチで説明しきれなくなる。以下を要件採否の判断基準とする。

| # | 判断基準 |
| :--- | :--- |
| C-1 | P-1 または P-2 のどちらかに直接効くか（どちらにも効かないものは将来拡張へ） |
| C-2 | 2分ピッチで、言葉を足さずに映像だけで伝わるか |
| C-3 | 8/22-23 の2日間で作り切れるか（既存要件の演出強化で済むものを優先する） |

## 2. サービス概要

| モード | 概要 |
| :--- | :--- |
| 平時モード（ゲーム） | LINEミニアプリ上の位置情報ゲーム。避難所チェックイン、現地クイズ、写真投稿ミッションでポイント・称号を獲得。投稿写真はVision AIが自動解析し、バリアフリー属性を構造化データとして蓄積。 |
| 有事モード（ライフライン案内） | 災害時に「災害ライフラインモード」へ切替。平時に蓄積したデータをもとに、避難所・水・電源・バリアフリー情報をマップで案内。 |
| 行政還元ダッシュボード | 収集データをヒートマップ・スコアリングで可視化し、データ空白地帯や優先整備箇所を行政へ提示。 |

### 2.1 独自の価値提案（UVP）と競争優位

> **「日常の『寄り道』を、都市を救う防災データに変える」**
> 平時は遊びながら無意識に防災訓練・データ収集を行い、有事は最強のライフライン案内に切り替わる「デュアルモード体験」。

競争優位（Unfair Advantage）は次の2点であり、要件上も中核として扱う。

| # | 優位性 | 対応する要件 |
| :--- | :--- | :--- |
| UA-1 | **超低コストのデータ収集**：市民の「遊び」が原動力となり、行政の調査予算に依存せずミクロデータが集まる | FR-02〜FR-05、FR-07（ゲーミフィケーション／インセンティブ） |
| UA-2 | **高精度検証：AI×群集心理の相互クイズ**：AI一次判定と、他ユーザーによる現地確認クイズの二段構えで精度を担保 | FR-05-2〜FR-05-5、**FR-06（相互検証）** |

> UA-2 を支える FR-06 は、単なる付加機能ではなく「収集データが行政に使える品質である」ことの根拠である。最小成立ライン（FR-06-1・FR-06-2）を Must とし、**デモシナリオには必ず1件の検証済みデータを含める**こと（5章 成功基準）。※Must格上げの承認は #1 で進行中。

### 2.2 ゲーム性の設計方針

ゲーム性は装飾ではなく、**要点 P-2（防災意識の低い層に防災情報をインプットする）を成立させる唯一の手段**である。広い年齢層に使ってもらうことを目的とするため、「防災に関心がなくても遊べる」状態を要件として扱う。

#### 設計原則（G-1〜G-7）

ゲーム性の本質は**「リスクとリターン」の駆け引き**にある。プレイヤーが危険や労力（リスク）を負い、その見返り（リターン）を得る揺らぎが面白さを生む。ただし本サービスは現実の街を舞台にするため、この原則をそのまま持ち込めない。以下を設計原則として固定する。

| # | 原則 | 本サービスでの意味 |
| :--- | :--- | :--- |
| **G-1** | ゲーム性とは「リスクとリターン」の駆け引きである | 報酬は必ず何らかの負荷と対で設計する。ノーリスク・ノーリターンの行動を並べても面白さは生まれない |
| **G-2** | **リスクを身体的危険に置き換えてはならない**（本サービス固有の最重要制約） | 「危険な場所へ行くほど高得点」は絶対に採らない。リスクは**時間・手間・移動距離・保有ポイントの消費・失敗の可能性・先取りの競争**に置き換える（NFR-14） |
| **G-3** | 一般性を優先し、ゲーム性は意図的に手加減する | ゲーム性を鋭くするほど初心者が脱落する。本サービスの目的は広い年齢層（シニア・要配慮者家族を含む）への普及であるため、上級者向けのスリルより「脱落者を出さないこと」を優先する。トレードオフを認識した上での決定であり、妥協ではない |
| **G-4** | 現実のモチーフを使い、説明を減らす | 実在の避難所・実在の防災グッズ・現実の街という題材そのものが、プレイヤーの持つ知識を利用できる。チュートリアルの代わりになり、説明不要で「歩く→点検する→報われる」のサイクルに入れる |
| **G-5** | 報酬には必ず「出口（消費先）」を用意する | 数値（ポイント）は消費先がないと徒労感になる。溜める楽しさは、消費するストレスと対になって初めて生まれる。MVPでも消費先を用意する。**FR-14 のカード収集がその出口になる** |
| **G-6** | 評価は労力とリスクに比例させる（当てたら偉い） | 「どれくらい良いことをしたか」で報酬を決める。手間の少ないチェックインは控えめに、二度足を運ぶ相互検証や未開拓ゾーンの初回投稿は大きく報いる（FR-07-1） |
| **G-7** | リトライは即座に、テンポを止めない | 失敗しても演出や待ち時間で冷ませず、すぐ操作権を戻す。間違えてもペナルティを与えず、必ず解説を見せて再挑戦させる（FR-04-6） |
| **G-8** | **モノより先に行動を教える** | 防災の話は備蓄品に寄りやすいが、発災直後に生死を分けるのは「まず身を守る」という**行動**である。備蓄が役に立つのはそれを生き延びた後であり、順序を取り違えると学習の順序も取り違える。クイズは「何を持つか」より「**まず何をするか**」を先に問い、アイテムの説明も行動を主語にする（FR-04-7、FR-07-8） |

> **G-8 の出どころ**：防災士講座で「発災直後はまず身を守る、生き残るのが先。死んだらため込んだグッズは使えない」と示された指摘に基づく。当初の要件はアイテム10種すべてを実在の防災グッズ（＝モノ）に置いており、**行動が抜けていた**。当事者の一次情報によって設計の偏りが見つかった例である（4.1 の CPF 検証状況も参照）。

> **G-1 と G-2 の緊張関係**が本サービスの設計上の最大の難所である。ゲーム性は危険と報酬の距離感から生まれるが、現実の街では「危険に近づく」ことを報酬で促した瞬間に、利用者を実害に晒す。したがって**駆け引きの舞台を現実空間から、時間・手間・リソース管理へ移す**。「大雨の日に川沿いへ行くと高得点」ではなく、「未開拓ゾーンは遠いが初回投稿の報酬が大きい」「保有ポイントを賭けて挑む高難度クイズ」のような形にする。

#### 実装対象の4軸

ゲーム要素は無限に思いつくため、判断基準 C-1〜C-3（1.2）で絞る。MVPでは次の4軸に整理し、**軸1・軸2を実装対象、軸3を将来拡張**とする。

| 軸 | ねらい | 具体化 | MVPでの扱い |
| :--- | :--- | :--- | :--- |
| **軸1 自慢・拡散** | 「SNSに上げたくなる」ものを報酬にし、獲得の喜びを拡散チャネルに変える | **カード（行動・道具・場所・ミッション）**、称号、シェア画像 | **実装**（**FR-14**／FR-07-7／FR-07-8） |
| **軸2 いい感じの頻度で何かが起こる** | 開くたびに変化があり、再訪の動機になる。オープンデータと天気を起点にするため本サービス固有の仕掛けになる | 場所・時期・天気に連動したイベント、隠れているものを探す | **実装**（FR-13 を Should） |
| **軸3 競争・協力** | 対戦相手に勝ちたい／他者と競い協力する動機 | ランキング、陣取り、対戦、協力ミッション、シーズン制 | **将来拡張**（EX-05）。参加人数が必要でコールドスタートに弱く、2日間では作り切れない |
| **軸4 短時間の達成感** | 「1回2分で終わる」体験に閉じ、歩きながら遊べるようにする | クイズ、間違い探し、リスクとリターン、期間ミッション | **既存要件で吸収**（FR-04）。演出強化で対応し、新規機能は追加しない |

**軸4を新機能にしない理由**：クイズ（FR-04）は既に Must で実装される。バトル・間違い探しは「クイズの出題形式と演出の違い」であり、機能を増やさず見せ方を変えるだけで成立する。判断基準 C-3 に最も合致する打ち手である。戦闘要素の企画案は `sample/battle-prototype/combat-overview.md` にプロトタイプ付きで存在するが、**採用可否は未定**（別Issueで判断する）。

> **安全設計の前提（G-2の具体化）**：報酬やイベントで危険な場所・危険なタイミングへ人を誘導してはならない。浸水想定エリアや川沿いを扱う場合も「近づいて遊べ」ではなく「ここは危ないと学べ」に着地させる。悪天候時・災害時はイベントとポイント倍率を抑制する（NFR-14）。

> **バランス調整の方針**：すべての要素を平均的な性能に均すのではなく、長所と短所がはっきりした「でこぼこ」を許容する。収集アイテムの効果（FR-07-8）は一律の数値強化ではなく、それぞれ得意な場面が違う形にする。ただし G-3 により、「使いこなせないと詰む」ほどの性能差は作らない。

## 4. ターゲットユーザー（顧客セグメント）

本サービスは「データを集める側」と「データを使う側」からなる**二面市場**として設計する。片側だけでは成立しないため、MVPでも両者の体験を最低限成立させる（データ活用者側は閲覧デモの範囲）。

さらにデータ収集者側は、**獲得の順序**を要件に織り込む。全セグメントを同時に狙うと、どのスポットも相互検証（UA-2）の閾値に到達せず、行政へ出せる検証済みデータが0件になるためである。

### 4.1 獲得フェーズ（初期ターゲットと拡大ターゲット）

| フェーズ | 対象 | 役割 | 到達チャネル |
| :--- | :--- | :--- | :--- |
| **フェーズ1（初期）** | 防災コミット層（[防災士](https://bousaisi.jp/license/)・[消防団員](https://www.fdma.go.jp/syobodan/)・防災意識の高い住民） | **データ提供者**。行政データに無いミクロデータの初期投入と相互検証を担い、後続ユーザーの「お手本」となる初期データをつくる | 自治体防災課・消防団の分団・防災士会の支部（既にリーンキャンバスのチャネル「自治体連携」に存在） |
| **フェーズ2（拡大）** | 一般層（位置ゲー層・アクティブシニア） | **データ拡張者／学習者**。ゲームとインセンティブを動機に参加し、遊びの副産物として防災知識をインプットする | LINE公式アカウント・LINE口コミ／SNSシェア・地域店舗のO2O |

初期ターゲットを防災コミット層に置く理由は次の3点。

1. **UA-2 が地理的な密度を要求する**：相互検証は同一スポットに複数人が訪れないと成立しない。受け持ちエリアが決まっている組織化された層（消防団の分団、防災士会の支部）なら、狭いエリアに濃い参加密度を最初からつくれる。
2. **獲得コストが低い**：窓口が自治体防災課・消防団・防災士会に集約されており、不特定多数の位置ゲー層へ広告的に届けるより桁違いに安い。
3. **初期データの品質が上がる**：何を記録すべきか（段差の高さ、開設状況、資機材の位置）を既に知っている層が最初のデータを作る。
4. **一般市民には物理的に取得できないデータを取れる唯一の層である**：スフィア基準の充足率算出に必要な便器数・男女別・夜間照明・要配慮者スペースはいずれも**避難所の内部情報**であり、指定避難所の多くは学校施設のため平時に一般市民は立ち入れない。**避難所運営訓練で内部に入る防災士・消防団員だけが取得できる**（9.1）。フェーズ1がフェーズ2の「お手本データ」を作るという構造は、この物理的制約によっても裏づけられる。

> MVP（〜First Stage）のヒアリング・デモ協力者は**フェーズ1の層から確保する**（5.1 PSF検証）。フェーズ2向けのゲーム性・インセンティブ要件（FR-02〜FR-07）はMVPでも実装するが、検証はフェーズ1の層で行う。

### 6.2 データストア（KVS）前提の設計方針

enebular データストアは JOIN・二次インデックス・集計・地理検索を持たない。9章の論理データモデルはそのままでは載らないため、**アクセスパターン起点でキーを設計する**。

| 制約 | 影響 | 対応方針 |
| :--- | :--- | :--- |
| 地理検索がない | `GET /spots?lat=&lng=&radius=` を範囲クエリで解けない | **エリアでパーティションを切る**（メインキー `area#<areaId>`）。エリア内の全スポットを取得し、距離計算はアプリ側で行う。デモ対象エリア限定（FR-10-3）なら件数が抑えられる |

**千代田区・港区は行政区ごとに分けず、1つのエリアパーティションへまとめて投入する。**
区ごとに分けると `GET /spots` が2クエリになり、探索率の分母も区ごとに割れる。撮影ルートは
区境をまたぐ1本なので、論理的にも1エリアが実態に合う。区の区別はスポットの `address` と
`source`（出典・取得日：FR-10-2）に残るため、FR-09 の自治体別集計は後から組み立てられる。
| 集計関数がない | KPI（5.2）を集計クエリで出せない | 行動記録と同時に**日次カウンタを加算**するテーブルを持つ（下表 `metrics`）。FR-11 は集計クエリ前提の記述からカウンタ前提へ読み替える |
| JOINがない | 投稿→ユーザー、投稿→検証の突合ができない | 参照側に必要な値を非正規化して持つ。検証は投稿IDをメインキーにして1回の取得で数えられる形にする |
| バイナリ格納に適さない | 投稿写真をデータストアに置けない | **CUCON（S3）に分離する**。データストアの `posts` にはオブジェクトキーのみを保持し、画像本体はCUCON側に置く |

初期のキー設計案（サンプル実装 `/sample` の実績設計を拡張したもの。確定は設計工程）。

### 6.3 AIエージェント（Dify）の構成方針

AI処理は個別のLLM API呼び出しを自前実装せず、**Dify 上のアプリとして開発する**。バックエンド（enebular）は Dify の App API を叩く薄いプロキシに留め、プロンプト・モデル選択・入出力スキーマ・実行ログは Dify 側に置く。

**この構成を採る理由**

- プロンプト改訂がデプロイなしで回る。ハッカソン当日（8/22-23）と First Stage 収録の間にプロンプトを詰める前提（14章のリスク対応）と相性が良い。
- 使用モデルを Dify 側の設定で差し替えられるため、モデル選定（#5）を実装と切り離して後追いで決められる。
- 画像解析→属性の構造化→不適切判定という多段処理をワークフローとして組めるため、バックエンドに分岐ロジックを持ち込まずに済む。

**MVPで用意するDifyアプリ**

| # | Difyアプリ | 入力 | 出力 | 対応FR |
| :--- | :--- | :--- | :--- | :--- |
| AI-1 | 画像属性抽出ワークフロー | 投稿写真、スポットカテゴリ、データ辞書の対象項目（FR-12-1） | 属性タグ候補の構造化JSON（項目キー・値・確信度） | FR-05-2 |
| AI-2 | 不適切画像・個人情報判定 | 投稿写真 | 判定区分（公開可／保留／却下）と理由 | FR-05-4、FR-05-6 |
| AI-3 | クイズ生成エージェント | スポット属性、周辺スポット、未取得項目 | 問題文・選択肢・正解・解説 | FR-04-2、FR-12-3 |
| AI-4 | 避難シミュレーションクイズ生成 | 現在地、周辺ハザード文脈 | 同上 | FR-04-4（Should） |

> AI-1 と AI-2 は1回の投稿で連続実行されるため、**1ワークフローに統合して1回の呼び出しに収める**ことを優先する（NFR-11のコスト制約：1投稿あたりの解析は1回）。

**境界の取り決め**

| 責務 | 置き場所 |
| :--- | :--- |
| プロンプト、モデル選択、出力スキーマ、リトライ | Dify |
| 呼び出し、タイムアウト制御、結果の永続化、ユーザーへの提示 | enebular バックエンド |
| AI出力の確定（ユーザー確認） | フロントエンド（FR-05-3、NFR-07） |

**確定事項**

| 項目 | 決定 |
| :--- | :--- |
| 利用形態 | **Dify Cloud**（SaaS）。セルフホストは行わない |
| モデル | **Gemini**（Google）。画像解析・クイズ生成いずれもGeminiを使用し、Dify側の設定で差し替え可能な状態を保つ |
| 認証情報 | Dify の App API キーは enebular 側の環境変数として保持する。Gemini のAPIキーは Dify のモデルプロバイダ設定側に置き、バックエンドからは触らない |

> Dify Cloud を使うため、投稿写真は解析時に外部SaaSへ送信される。プライバシー方針（NFR-06）と同意画面（FR-01-4）の文面に、AI解析のために画像を外部サービスへ送信する旨を含めること。

#### 9.1 スフィア基準に基づく充足率の算出

スフィア基準（Sphere Standards）は人道支援における最低基準であり、避難所の生活環境について数値目標を持つ。日本の避難所はこの基準に対して大きな開きがあることが、熊本地震・能登半島地震の検証で繰り返し指摘されている。

**算出できる指標（MVP対象）**

| 指標 | 基準 | 算出式 | 必要な属性 |
| :--- | :--- | :--- | :--- |
| **トイレ充足率** | 避難者 **20人に1基** | `収容想定人数 ÷ 便器数` を「1基あたり何人か」として算出し、20人以下なら充足 | 便器数（市民投稿）＋ 収容想定人数（オープンデータ） |
| **男女別トイレ** | 男女比 **1:3** | 男女別の基数比を判定。共用のみの場合は未充足 | 男女別／共用の別（市民投稿） |
| **夜間照明** | 夜間利用の安全確保 | 照明の有無で判定 | 夜間照明の有無（市民投稿） |
| 居住面積 | 1人あたり **3.5㎡** | `延床面積 ÷ 収容想定人数` | **市民投稿では取得不能**。公共施設データの延床面積と収容想定人数から算出できる場合のみ（FR-12-6 の考え方で既存データを優先） |

> **トイレを最優先とする理由**：断水や不衛生、夜間の暗さによってトイレ利用が忌避されると、避難者が**意図的に水分摂取を控える**。これが脱水と血液濃縮を招き、静脈血栓塞栓症（エコノミークラス症候群）の主要因となる。能登半島地震では、断水でトイレが使えず屋外へ向かった高齢者が転倒し低体温症で死亡した事例も報告されている。**トイレは快適性の問題ではなく死因の起点**であり、収集項目としても可視化指標としても最優先に置く。

**3状態で表示する**

充足率は「充足／未充足」の二値ではなく、**「判定不能（データ未取得）」を第3の状態**として明示する。未取得の避難所が地図上で色分けされることで、FR-09-2（データ空白地帯）と FR-12（欠損の抽出）がダッシュボード側でも接続され、**行政から見て「まず何を調べるべきか」が分かる**。

**この要件が持つ意味**

市民の投稿は「◯件集まりました」という量の報告に留まる限り、行政の意思決定には使いにくい。**国際基準という外部の物差しを通すことで、「この区の避難所の◯割がトイレの基準を満たしていない」という、そのまま整備計画の根拠になる形へ変換される。** UA-1（超低コストのデータ収集）の出力が、行政にとっての実用値になる接点がここである。

**制約**

- 収容想定人数はオープンデータ側に存在する前提である。取込対象データセットに当該列があるかを FR-10 の取込時に確認すること
- 便器数・男女別・夜間照明は**避難所の内部情報**であり、指定避難所の多くは学校施設のため**平時に一般市民が立ち入れない**。この項目群は主に**フェーズ1層（防災士・消防団員。避難所運営訓練で内部に入る）**が担う（4.1）。データ辞書（FR-12-1）では「平時に外から観測できる項目」と「訓練時・開設時にしか取得できない項目」を区別する

### FR-12 不足データの抽出とクエスト化

要点 P-1（行政データの不足を補う）を機能として具体化する要件。従来の FR-02-3／FR-02-4（未開拓ゾーン）は「投稿・検証数が少ない**スポット**」を単位にしていたが、本要件は「そのスポットで**まだ埋まっていない属性項目**」まで解像度を上げ、ユーザーに**何を答えてほしいかを名指しで問う**。

前提として **収集対象の防災データ項目リスト（データ辞書）が必要**であり、この定義は未決である（#14 で確定させる）。行政オープンデータに既に存在する項目は対象外とし、「行政データに無いが避難行動に必要な項目」を収集対象とする。

| ID | 要件 | 優先度 |
| :--- | :--- | :--- |
| FR-12-1 | 収集対象の属性項目をスポットカテゴリごとに定義した**データ辞書**をサーバー側に持ち、更新可能にする | M |
| FR-12-2 | スポットごとに、データ辞書の項目に対する**充填状況（未取得／AI提案／ユーザー確定／検証済み）を判定**する | M |
| FR-12-3 | スポット詳細で「このスポットに足りない情報」を未取得項目として提示し、その項目を埋める投稿・回答へ導線を張る | M |
| FR-12-4 | 未取得項目の充填にポイント倍率を付与する（FR-02-4 の倍率判定を項目単位に統合する） | S |
| FR-12-5 | 行政還元ダッシュボードで、エリア×項目の充填率を可視化する（FR-09-2 のデータ空白地帯表示を項目軸に拡張） | S |
| FR-12-6 | 取込済みオープンデータの列と突合し、行政データに既に存在する項目は収集対象から自動的に外す | C |

> FR-12 は行政側から見た「何が足りないか」と、ユーザー側から見た「何を答えれば貢献になるか」を同じデータ辞書で結ぶ。これによりUA-1（超低コストのデータ収集）が、単なる物量ではなく**行政が欲しい項目に向いた収集**になる。

### FR-14 カードコレクション（行動・道具・場所・ミッション）

出題・道具・スポット・ミッションを**すべて「カード」という一つの器**で扱い、集める対象にする。

**これは機能の追加ではなく統合である。** ばらばらに並んでいた報酬（バッジ・アイテム・ポイントの交換先・ミッション）を
1つの形にまとめることで、要件と画面をむしろ減らしている。

| 統合される要件 | 統合後の扱い |
| :--- | :--- |
| FR-04-5（ミッション配信） | **ミッションカード**になる |
| FR-07-6（デジタルバッジ） | カードに置き換わる（バッジは作らない） |
| FR-07-9（ポイントの消費先） | **カードそのものが出口**になるため、交換所を作らない（G-5 を満たす） |

#### カードの4種と達成条件

カードは **達成／未達成** の2状態のみを持つ。中間状態は設けない。

| 種類 | カードの中身 | 未達成（**仮に所持**） | 達成（**自分のもの**） |
| :--- | :--- | :--- | :--- |
| **行動カード** | まず何をするか（例：「揺れたら頭を守る」） | 出題されたが正解していない | クイズに正解した |
| **道具カード** | 何を使うか（例：「携帯トイレ」） | どこで手に入るかは分かる | 獲得した |
| **場所カード** | どこへ行くか（避難所・AED・トイレ・給水） | 地図に見えている | チェックインした |
| **ミッションカード** | 何を達成するか | 条件が示されている | 条件を満たした |

> **「行動」を1種目に置いているのは G-8 の具体化である。** 道具より先に行動が並ぶことで、
> 「モノをそろえれば備えたことになる」という逆の学習を、分類そのもので防ぐ。

#### 未達成カードの見せ方

未達成は「持っていない」ではなく「**まだ自分のものになっていない**」として見せる。
カードの枠は最初から並んでおり、**何が残っているかが常に見えている**状態にする。

| 未達成で見せるもの | 未達成で隠すもの |
| :--- | :--- |
| 種類・タイトル・**どうすれば達成できるか** | 中身（行動の解説、道具の使い方、ミッションの報酬） |

**未達成のカードはデータとして保存しない。** 定義から導出して表示するだけにする。
保存すると書き込み回数が「歩いた量」ではなく「カードの総数」に比例してしまう（6.2 の方針と整合）。

| ID | 要件 | 優先度 |
| :--- | :--- | :--- |
| FR-14-1 | 4種のカードを同一の型で扱い、1つの一覧に表示する。種類で絞り込める | M |
| FR-14-2 | 各カードは**達成／未達成**の2状態を持つ。達成日時を保持する | M |
| FR-14-3 | 未達成カードは種類・タイトル・達成条件のみを表示し、中身は隠す | M |
| FR-14-4 | **場所カード**：対象スポットへのチェックインで達成する（FR-03） | M |
| FR-14-5 | **行動カード**：対応するクイズへの正解で達成する（FR-04・FR-04-7） | M |
| FR-14-6 | **道具カード**：チェックインまたはクイズ正解による獲得で達成する（FR-07-8） | M |
| FR-14-7 | **ミッションカード**：他のカードの達成枚数を条件として判定する（下表） | M |
| FR-14-8 | 達成した瞬間に演出を表示する（カードが裏から表に返る等） | S |
| FR-14-9 | 達成したカード1枚を、そのままシェア画像として出力できる（FR-07-7 と共通） | S |
| FR-14-10 | **レア度・希少性を場所に紐づけてはならない**。「危険な場所のカードは希少」は報酬で危険箇所へ誘導することになる。序列を付ける場合は**行動の重要度**に紐づける（G-2・NFR-14） | M |
| FR-14-11 | **デッキ構築・合成・進化・対戦は実装しない。**「集めて眺める」までに留める。カードゲームとして複雑化させると、シニアや要配慮者家族が脱落する（G-3） | M |
| FR-14-12 | カードは「データを出したこと」に対して与える。収集自体が目的化すると、本来集めたい街の安全データより収集に関心が向く | M |

#### MVPで用意するミッションカード

**追加のデータを持たず、他のカードの枚数を数えるだけで判定する。**

| ミッション | 達成条件 |
| :--- | :--- |
| まず身を守る | **行動カード** 1枚 |
| 避難所を3か所たずねる | **場所カード**（避難所）3枚 |
| AEDを2か所見つける | **場所カード**（AED）2枚 |
| だれかの投稿を確かめる | 相互検証への回答 1回（FR-06-1） |

#### データ設計

**新しいテーブルを作らない。** 既存の所持アイテムのテーブルを流用し、サブキーに入れる値を
カードの識別子へ一般化する（6.2）。

```
user_items   userKey = "user#<uuid>"   itemKey = "tool:helmet"
                                                "place:sample-hibiya-park"
                                                "action:shelter-action-1"
                                                "mission:shelter-3"
```

> サブキーの列名が `itemKey` のまま「カードの識別子」を持つことになる。
> 名前と中身がずれるが、**テーブルを作り直す手間を避けるほうを選んだ**（enebular コンソールでの
> テーブル追加が要らない）。命名の由来をここに残す。

## 9. データモデル（論理）

主要エンティティのみ。詳細な物理設計は設計工程で確定する。

```
users              ユーザー（LINE userId、表示名、累計ポイント、属性設定、最終アクティブ日時）
spots              スポットマスタ（名称、カテゴリ、緯度経度、出典、出典取得日、初回データ付与日時、最終更新日時）
spot_attributes    スポット属性タグ（車いす対応等、値、ステータス: AI提案/ユーザー確定/検証済み、由来投稿ID）
checkins           チェックイン（ユーザー、スポット、日時、位置）
posts              写真投稿（ユーザー、スポット、CUCONオブジェクトキー、AI解析結果JSON、ステータス: 保留/公開/却下）
verifications      相互検証（投稿、ユーザー、賛否、コメント）
quizzes            クイズ（スポット、問題文、選択肢、正解、生成元、キャッシュ用）
quiz_answers       回答履歴（ユーザー、クイズ、正誤）
point_logs         ポイント履歴（ユーザー、種別、行動種別、増減、日時）
titles             称号（ユーザー、スポット、称号名、期間）
cards              達成したカード（ユーザー、カード識別子: <種類>:<キー>、達成日時、個数）
                   ※ 未達成カードは保存せず、定義から導出する（FR-14）
events             イベント（発生条件: エリア・カテゴリ・期間・天気条件、報酬、有効フラグ）
notifications      アプリ内通知（ありがとう通知等）
```

これに加えて、データ辞書（FR-12-1）と日次カウンタを持つ。

```
attribute_dictionary  収集対象の属性項目定義（カテゴリ、項目キー、データ型、選択肢、行政データに存在するか）
metrics               日次カウンタ（日付、指標キー、値）
```

> **KVSであることの影響**：本章は論理モデルであり、物理的にはJOIN・集計・地理検索を持たないenebularデータストアへ 6.2 のキー設計で落とす。KPI（5.2）は集計クエリではなく、行動記録時に `metrics` を加算する方式で取得する（FR-11）。`spots.初回データ付与日時 / 最終更新日時` は新規・更新スポット数の算出に用いる。

### データステータス遷移（投稿・属性）

```
投稿 → AI一次判定 ─ NG → 保留/却下
              └ OK → 公開（属性は「AI提案→ユーザー確定」）
                        └ 相互検証 賛成が閾値到達 → 検証済み → ダッシュボード/CSV出力対象
```

## 13. 前提条件・制約

- LINE Developersアカウント・**LINE公式アカウント**・LIFFアプリ（開発版）をチームで用意できること。
- **enebularのクラウド実行環境とデータストアをチームで利用できること**（ZIP / Node.js 22.x、デプロイ手段を含む）。
- **Dify Cloud のワークスペースとApp APIキーを用意できること**（6.3）。
- **Gemini のAPIキーと予算**（デモ規模の従量課金）を確保し、Dify のモデルプロバイダとして設定できること。実行環境がenebularのため、推論はすべて外部呼び出しになる。
- **CUCON（S3）のバケットとアクセス認証情報**を用意できること（投稿写真の保存先）。
- **Mapbox のアカウントとアクセストークン**を用意し、デモ規模のマップロード数が無償枠に収まることを確認できること。
- FR-13（イベント発生）を実装する場合、**天気情報APIを選定しキーを確保できること**（6.1）。
- 収集対象の防災データ項目（データ辞書：FR-12-1）を8/22までに一次確定させること（#14）。
- 初期ターゲット（防災士・消防団員等）への到達ルートを、ヒアリング・デモ協力の依頼が出せる状態にしておくこと（4.1）。
- オープンデータは**千代田区・港区**分を8/22までに取込済みにすること（FR-10、#6 決着）。港区 AED は GeoJSON のため、取込スクリプトが CSV と GeoJSON の両方を扱えること。
- 実機デモはLINEアプリ上で行う。未認証ミニアプリのため、参加者以外への一般公開は行わない。
- 位置偽装（GPSスプーフィング）への完全な対策はMVPでは行わない（位置整合性チェックのみ）。

## 14. リスクと対応

| リスク | 影響 | 対応 |
| :--- | :--- | :--- |
| ハッカソン2日間でMust要件が完了しない | デモ不成立 | 事前準備（8/22以前）でオープンデータ取込・LIFF疎通・AI解析のPoCを済ませ、当日は結合とUIに集中する |
| Vision AIの属性抽出精度が不十分 | デモ品質低下 | デモ用写真セットで事前にプロンプトをチューニング（Difyのため再デプロイ不要）。タグはユーザー修正可能な設計（FR-05-3）で精度不足を吸収 |
| Dify Cloud（AI基盤）の障害・レイテンシ・レート制限 | 写真投稿とクイズが止まりデモが不成立 | 呼び出しにタイムアウトと再試行を実装（NFR-02）。デモ用にAI-1/AI-3のフォールバック（固定のタグ候補・事前生成クイズ）を用意し、AI応答なしでもフロー全体は通す |
| Mapbox の無償枠（月間マップロード）を超過する | 課金発生、または表示停止 | デモはクローズド環境かつ対象エリア限定で実施し、ロード数を抑える。トークンにURL制限を設定し、想定外の利用を防ぐ |
| データストアに地理検索・集計がない | マップ表示遅延、KPIが出せない | エリアパーティション＋アプリ側距離計算、日次カウンタ方式で対応（6.2）。デモエリア限定でデータ量を制御 |
| CUCON（S3）への疎通・権限設定が当日までに済まない | 写真投稿（FR-05）が動かずデモ不成立 | 8/22前にアップロード・取得の疎通を確認する。暫定回避としてリサイズを強めた小サイズ画像をデータストアに保持する経路を残す |
| 初期ターゲット（防災士・消防団）への到達が間に合わない | フェーズ1の参加者が集まらず、相互検証が回らない | 自治体防災課・防災士会・消防団分団への依頼を先行着手。First Stageまでに間に合わない場合はチームメンバー＋知人の防災コミット層で最小密度を確保する |
| 不適切投稿がデモ中に発生 | 信頼性毀損 | AI一次フィルタ＋保留フロー（FR-05-4）。デモはクローズド環境で実施 |
| LIFFの位置情報取得の精度・拒否 | チェックイン不可 | 位置許可の導線を丁寧に設計。デモ用に閾値を緩和できる設定を持つ |
| ゲーム性を高めた結果、シニア・要配慮者家族が脱落する | 広い年齢層への普及（P-2）が達成できず、二面市場の片側が崩れる | G-3 により一般性を優先すると明示的に決定済み。競争・対戦要素（軸3）を将来拡張に固定し、難易度の救済措置（クイズは不正解でもペナルティなし・再挑戦可：FR-04-6）を必須実装とする |
| ポイントが貯まるだけで使えず徒労感を生む | 継続率の低下。報酬設計が機能しない | **FR-14 のカードが出口になる**（G-5）。集める対象があること自体が消費先として働くため、交換所を作らずに解消する |
| カード収集が目的化し、街の安全データより収集に関心が向く | 本来集めたいデータが集まらない | カードは「データを出したこと」に対して与える（FR-14-12）。レア度は場所に紐づけない（FR-14-10）。デッキ構築等の複雑化も行わない（FR-14-11） |
| ゲーム要素の検討が発散し、Must要件の実装時間を圧迫する | デモ不成立 | 判断基準 C-1〜C-3（1.2）で採否を判断し、軸3（競争・協力）は将来拡張に固定する（2.2）。新規機能より既存要件の演出強化を優先する |
| 報酬・イベントが危険な場所や悪天候時の外出を誘発する | 利用者の安全に関わる重大リスク。審査でも致命的 | FR-13-6・NFR-14 を必須条件として実装。災害の擬人化等の表現を採る場合は `sample/battle-prototype/combat-overview.md` 6章の配慮を前提とする |
| 参加人数が少なく相互検証（UA-2）が閾値に達しない | 競争優位の実証ができず、検証済みデータが0件になる | デモでは検証閾値を賛成1〜2件に設定可能にする。チームメンバーによる検証回答をシナリオに組み込み、必ず1件は検証済みに到達させる（5.1） |
| データ活用者（ペルソナ④・自治体）側の価値がデモで伝わらない | 二面市場のうち片側のみの訴求となり、協創ストーリーが弱くなる | ピッチ・デモ構成に「収集→ダッシュボード反映→要配慮者が閲覧」の受け手側カットを必ず含める |
